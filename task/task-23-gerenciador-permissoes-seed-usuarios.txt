TASK 23 - Gerenciador de permissões (superadmin) + seed de usuários
================================================================================

OBJETIVO
--------
A task-3 (seção 6) já instalou o spatie/laravel-permission, o
Gate::before do Super Admin e o PermissionSeeder/RoleSeeder completos
(precisou ser antecipado pra lá porque rotas de tasks anteriores a esta
já dependiam do middleware permission:*). Mas nunca existiu uma TELA
pra gerenciar isso — hoje só dá pra mudar via seeder/tinker, redeploy.
Esta task adiciona o gerenciador de papéis/permissões pro superadmin
(replicando o mesmo padrão já usado no projeto adm do ecossistema
Celke) e cria o seeder com os usuários de TESTE/demonstração do
projeto (esse sim, novo aqui).


1. PADRÃO REPLICADO DO PROJETO ADM
-----------------------------------------
Levantado no próprio celke-nota-corte-administrativo-v1-adm:

  - RoleController: CRUD de papéis (index/create/store/edit/update/
    destroy) + updateOrder (reordena papéis; o papel "Super Admin" é
    sempre order=1 e não pode ter a ordem alterada).
  - PermissionController: CRUD de permissions (title + name) — lista
    simples, sem agrupamento por módulo.
  - RolePermissionController: a tela de ATRIBUIR permissions a um
    papel — index($role) lista TODAS as permissions com um indicador
    "Liberado"/"Bloqueado" por linha; update($role, $permission) faz
    TOGGLE (givePermissionTo/revokePermissionTo) e redireciona de
    volta. Bloqueia explicitamente essa tela quando $role->name ==
    'Super Admin' (não há o que atribuir — ver item 2).
  - Gate::before em AppServiceProvider: quem tem o papel 'Super Admin'
    passa em QUALQUER ability automaticamente, sem precisar de cada
    permission atribuída uma a uma.
  - Middleware permission:<nome-da-permission> em cada rota
    individualmente (não em grupo).

Replicar essa MESMA estrutura aqui, só adaptando os nomes de permission
já usados nas tasks deste projeto (convenção "recurso.acao", ex.
car-washes.approve — diferente do "acao-recurso" hifenizado do adm,
mas a ideia é a mesma).


2. GATE::BEFORE (JÁ INSTALADO NA TASK-3, SEÇÃO 6)
---------------------------------------------------------
O bypass total do Super Admin (`Gate::before` no AppServiceProvider) já
foi feito na task-3 — aqui só usamos o resultado dele:
RolePermissionController::index() bloqueia o acesso à tela de
atribuição quando a role é 'Super Admin' (não há o que atribuir, ele já
passa em tudo), igual ao adm.


3. PERMISSIONS DE GERENCIAMENTO (JÁ SEEDADAS NA TASK-3)
------------------------------------------------------------------
  roles.index / .create / .edit / .destroy / .update-order
  permissions.index / .create / .edit / .destroy
  role-permissions.index / .update

Essas 3 linhas já existem no banco desde a task-3 (seção 6, lista
consolidada) — aqui só construímos as TELAS que as usam. Reservadas de
propósito: o RoleSeeder (também já na task-3) só dá essas permissions
pro papel "Super Admin" (via bypass do Gate::before, nem precisa
atribuir de fato) — o papel "Administrador" NÃO as recebe, então não vê
"Papéis"/"Permissões" no menu (task-14, sidebar condicional por
permission). Se um dia precisar que outro papel administre isso
também, é só o Super Admin ir na tela e atribuir — sem precisar de
código novo.


4. ROTAS (RESUMO)
-----------------------
Admin (cada rota com seu próprio middleware permission:<nome>):
  GET/POST  /admin/roles
  GET/PUT   /admin/roles/{role}
  DELETE    /admin/roles/{role}
  POST      /admin/roles/{role}/update-order
  GET/POST  /admin/permissions
  GET/PUT   /admin/permissions/{permission}
  DELETE    /admin/permissions/{permission}
  GET       /admin/role-permissions/{role}
  GET       /admin/role-permissions/{role}/{permission}   (toggle)

TASK 14 - Layout do painel (dashboard, sidebar, componentes reutilizáveis)
================================================================================

OBJETIVO
--------
Construir a estrutura visual compartilhada dos dois painéis autenticados
do projeto — admin (/admin/*) e lava-rápido (/painel/*) — antes de
qualquer tela de CRUD específica ser construída. A task-6 já definiu a
paleta de cores e as classes Tailwind; esta task define a ESTRUTURA
(layout, sidebar, dashboard, componentes) que usa essa paleta.

Sem isso, cada task de tela (4, 5, 9, 10, 11) acabaria inventando sua
própria estrutura de página — este é o pré-requisito prático que evita
isso.

ATENÇÃO DE ORDEM (2026-07-17): esta task roda LOGO depois da task-6 na
ordem de execução — ou seja, ANTES das tasks 4/5/9/10/11, que são quem
realmente registra as rotas que a sidebar abaixo lista (car-washes.index,
payment-gateways.index, orders.index etc.). Se cada item do menu chamar
route('nome') direto, a página quebra (RouteNotFoundException) assim
que uma rota ainda não registrada for referenciada — e como a sidebar
aparece em TODO layout autenticado, isso quebraria literalmente
qualquer tela construída entre esta task e a task em que a rota
correspondente nascer. Por isso, todo item do menu (seções 2 e 3
abaixo) precisa checar Route::has('nome-da-rota') antes de tentar
montar o link — se a rota ainda não existe, o item simplesmente não
aparece (sem erro), e passa a aparecer sozinho assim que a task
correspondente registrar a rota, sem precisar tocar nesta task de novo.
(O pacote spatie/laravel-permission em si, usado pelo @can abaixo, já
foi instalado antecipadamente na task-3, seção 6 — então os `@can`
funcionam desde já, só as ROTAS específicas de cada tela é que nascem
aos poucos.)

--------------------------
Itens de menu — cada um só aparece se o admin logado tiver a permission
correspondente (spatie/laravel-permission, task-11):

  Dashboard

  Planos de repasse                     (payout-plans.index)

Os contadores dos badges são queries diretas (count), sem necessidade
de cache/job na v1 — o volume esperado não justifica a complexidade
extra ainda.

Implementação de cada item do menu (array de config, não Blade solto):
  ['label' => 'Lava-rápidos', 'route' => 'car-washes.index',
   'permission' => 'car-washes.index']
O componente/partial que itera essa lista só renderiza o item se
Route::has($item['route']) E auth()->user()->can($item['permission'])
— as duas checagens, nessa ordem (rota primeiro, mais barata). Isso
resolve o "ATENÇÃO DE ORDEM" do topo deste arquivo.

2.1 ÍCONE EM CADA ITEM DO MENU
- - - - - - - - - - - - - - - - - -
Uma sidebar com ~20 itens só de texto vira um paredão difícil de
escanear. Cada item ganha uma quarta chave, 'icon', com O ATRIBUTO "d"
de um path do Heroicons outline (24x24, stroke) — só o "d", sem markup:

  ['label' => 'Pedidos', 'route' => 'orders.index',
   'permission' => 'orders.index', 'badge' => null,
   'icon' => 'M15.75 10.5V6a3.75 3.75 0 10-7.5 0v4.5m11.356-1.993...']

Por que só o "d" e não o <svg> inteiro: quem decide tamanho, cor e
estado (ativo/hover) é o layout, não o array de config. Ícone que já
vem com class="w-5 h-5 text-gray-400" embutido obriga a editar 20
strings pra mudar o tamanho da sidebar. Ícones com mais de um traço
concatenam os subpaths no mesmo "d" (path SVG aceita vários "M").

Não instalar pacote de ícones pra isso — são ~20 paths copiados uma vez
do heroicons.com, sem dependência nova nem passo de build.

A view monta o <svg> em volta:

  <svg class="h-5 w-5 shrink-0 {{ $isActive ? 'text-blue-400'
              : 'text-gray-500 group-hover:text-gray-300' }}"
       fill="none" stroke="currentColor" stroke-width="1.6"
       viewBox="0 0 24 24" aria-hidden="true">
      <path stroke-linecap="round" stroke-linejoin="round" d="{{ $item['icon'] }}" />
  </svg>

O link vira "group flex items-center gap-3" (com o label em
<span class="flex-1"> pra empurrar o badge pra direita), e o ícone do
item ativo fica azul — reforça o estado ativo além do fundo.

Teste: um loop garantindo que TODO item de AdminMenu::items() tem
'icon' preenchido, e que a sidebar renderizada contém '<svg'. Sem isso,
item novo acrescentado numa task futura entra sem ícone e desalinha a
lista inteira.

visível só quando o usuário tem mais de 1 car_wash vinculado — mesmo
mecanismo já descrito na task-5, seção 7.

IMPORTANTE pra testabilidade (ver task-13): a regra de "quais itens
aparecem" NÃO deve ficar espalhada em @if direto no Blade da sidebar —
extrair pra uma classe simples (ex: App\Support\CarWashPanelMenu),
recebendo os produtos ativos + o role do usuário naquele car_wash e
devolvendo a lista de itens visíveis. A view só chama essa classe e
itera o resultado. Isso é o que permite testar a REGRA como teste
unitário (sem HTTP/banco), em vez de precisar montar uma requisição
completa pra cada uma das combinações possíveis.

Diferente da sidebar do admin, os itens da sidebar do lava-rápido
(Confirmar lavagem, Lavagens, Repasses, Estacionamento...) só nascem em
tasks que rodam DEPOIS desta (8, 9, 10) — mesmo Route::has() defensivo
da seção 2 se aplica aqui, dentro da própria CarWashPanelMenu.

6. COMPONENTES BLADE REUTILIZÁVEIS
----------------------------------------
Além do <x-badge> já definido na task-6:

  <x-card>            container padrão com título opcional
  <x-stat-tile>        número grande + label, usado nos dashboards (KPIs
                       e resumos de produto)
  <x-data-table>       tabela com paginação, cabeçalho ordenável, e
                       estado vazio embutido (usa <x-empty-state> por
                       padrão quando não há linhas)
  <x-empty-state>      ícone + mensagem curta, usado em toda listagem
                       vazia (ex: "Nenhum lava-rápido pendente",
                       "Nenhuma lavagem ainda")
  <x-confirm-modal>    confirmação antes de ações destrutivas/
                       irreversíveis (aprovar, rejeitar, suspender,
                       marcar como pago) — evita clique acidental numa
                       ação sem volta, principalmente as financeiras
  <x-form-field>       wrapper de label + input + erro de validação,
                       padroniza os formulários das tasks 4/5/7/9/10/11
                       (evita repetir a mesma estrutura de
                       @error/label em cada view)

Construir esses componentes AQUI, antes das telas de CRUD, é o que
permite que as tasks seguintes só consumam (<x-data-table :rows="...">)
em vez de reinventar tabela/paginação/estado-vazio a cada tela nova.

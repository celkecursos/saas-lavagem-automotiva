TASK 4 - Pagamentos: gateway dinâmico multi-provedor (PagSeguro, Mercado Pago,
Hotmart etc.)
================================================================================

OBJETIVO
--------
Permitir aceitar pagamento por vários provedores diferentes, cada um com sua
própria implementação de código, e o ADM escolher qual está ATIVO
diretamente pelo painel administrativo (sem precisar mexer em código/deploy
pra trocar de gateway). V1 usa PagSeguro (PagBank), no ambiente sandbox
(conta PJ já disponível). Mercado Pago, Hotmart etc. entram depois só como
uma nova classe, sem mudar a estrutura.

Este desenho é uma cópia adaptada do padrão já validado e implementado no
projeto Celke Payments (task #14 lá) — mesmo padrão de "Strategy resolvido
por linha de banco" que o `AiServiceFactory` usa pra IA (OpenAI/Claude/
Gemini) naquele ecossistema. Reaproveitar a mesma arquitetura aqui evita
reinventar decisões já testadas.

2. CONTRATO (INTERFACE) QUE TODO GATEWAY PRECISA IMPLEMENTAR
------------------------------------------------------------------

  interface PaymentGatewayInterface
  {
      public function createCheckout(Order $order): CheckoutResult;
      public function handleWebhook(Request $request): WebhookResult;
      public function verifySignature(Request $request): bool;
      public function refund(Order $order): bool;   // false = gateway não
                                                      // suporta via API,
                                                      // cai pra processo
                                                      // manual do admin

      // Cobrança automática de renovação, usando um cartão já salvo —
      // NÃO é um checkout (o assinante não vê/faz nada). Ver seção 5
      // sobre por que a recorrência é "manual" (nós disparamos), não
      // o gateway sozinho.
      public function chargeSavedMethod(Order $order, PaymentMethodToken $method): ChargeResult;
      public function supportsSavedCardRecurring(): bool;  // false =
                                                            // gateway não
                                                            // suporta;
                                                            // task-7 trata
                                                            // como falha
                                                            // de renovação
  }

  CheckoutResult (DTO): tudo que a view de checkout precisa pra montar a
  tela — url de redirect (quando checkout_mode = redirect) OU dados pro
  formulário embutido (quando checkout_mode = embedded).

  WebhookResult (DTO): status resultante ('paid'/'failed'/'refunded'/
  'chargeback'), externalReference (id da transação no gateway) E
  orderReference (a NOSSA referência que o gateway ecoa de volta — sem
  isso o controller do webhook não sabe a qual Order o evento pertence).

  ChargeResult (DTO): status ('paid'/'failed'), externalReference,
  failureReason (nullable — motivo devolvido pelo gateway quando o
  cartão salvo falha, ex: "cartão expirado", exibido no e-mail de
  past_due da task-7).


3. FACTORY (RESOLVE QUAL GATEWAY ESTÁ ATIVO)
--------------------------------------------------

  class PaymentGatewayFactory
  {
      public static function make(): PaymentGatewayInterface
      {
          // busca payment_gateways ativo (is_active = true)
          // zero ativos            -> lança PaymentGatewayNotConfiguredException
          // mais de um ativo (corrida) -> escolhe o de updated_at mais
          //                              recente + Log::warning
          //                              (nunca derruba o checkout)
          // resolve $gateway->type->service_class, class_exists() + new
      }

      public static function resolveActiveGateway(): ?PaymentGateway
      {
          // só o model, sem instanciar a classe — usado no momento de
          // CRIAR o pedido (pending), pra já gravar qual gateway vai
          // processar antes do pagamento acontecer (não só no
          // markPaid())
      }
  }

  Isso é o que permite o ADM trocar de gateway sem deploy: troca a linha
  is_active em payment_gateways, a próxima chamada de make() já resolve
  pro novo.

5. GATEWAY CONCRETO v1: PAGSEGURO (SANDBOX)
------------------------------------------------
PagBank (PagSeguro) tem ambiente sandbox oficial para testes antes de ir
pra produção com a conta PJ real. Não existe SDK Composer oficial
mantido — a integração é via API REST (usar o Http client do próprio
Laravel: Http::withToken(...)->post(...)).

Passos desta fase:
  1. Criar conta de sandbox no PagBank seguindo o passo a passo oficial:
     https://developer.pagbank.com.br/docs/crie-sua-conta-pagbank#sandbox
     — gera token de API separado do ambiente de produção, sem precisar
     de dados reais da conta PJ pra testar o fluxo inteiro antes de ir
     pra produção.
  2. Seed de payment_gateway_types com a linha 'pagseguro' ->
     service_class = App\Services\Payment\PagSeguroGateway,
     checkout_mode = 'embedded' (ver 5.1 sobre por que não dá pra usar
     'redirect' pra assinatura recorrente).
  3. Implementar PagSeguroGateway implements PaymentGatewayInterface:
     - createCheckout(): POST na API de Orders do PagBank
       (https://sandbox.api.pagseguro.com/orders em sandbox). Se
       Order.recurring_type='initial', o corpo inclui card.encrypted —
       UM ÚNICO blob criptografado que já contém titular/número/
       validade/CVV juntos (gerado no browser via
       PagSeguro.encryptCard(), ver seção 5.3 — o CVV NUNCA trafega
       separado nem em texto puro, nem pro nosso backend nem pro
       PagBank), mais recurring.type="INITIAL", store=true. A resposta
       traz um card.id — grava em payment_method_tokens.
     - chargeSavedMethod(): POST na MESMA API de Orders, mas com
       card.id (de payment_method_tokens) + recurring.type=
       "SUBSEQUENT" — cobrança direta, sem o assinante ver nada. É
       assim que o scheduler de renovação (task-7, seção 4) cobra
       automaticamente.
     - supportsSavedCardRecurring(): retorna true.
     - handleWebhook(): valida payload do PagBank, resolve
       orderReference e status.
     - verifySignature(): header x-authenticity-token = SHA256
       ("{token}-{payload_bruto_sem_formatar}") — comparar com o hash
       calculado localmente usando o token da conta. Payload TEM que
       ser usado exatamente como recebido (espaço/formatação a mais
       já quebra o hash).
     - refund(): chama API de reembolso do PagBank (retorna true se
       processou; false se não suportado nesse fluxo específico, cai
       pra manual).
  4. Criar payment_gateways com sandbox_mode = true, is_active = true,
     credentials = token de sandbox.
  5. Testar end-to-end no sandbox: 1º pagamento (INITIAL) tokeniza e
     salva o cartão -> segunda cobrança simulando o scheduler chama
     chargeSavedMethod() direto (SUBSEQUENT) sem passar por nenhuma
     tela -> confirma que gera um novo order 'paid' e um
     subscription_cycles novo (task-7).

Mercado Pago e Hotmart ficam para tasks futuras — quando chegar a hora,
é só repetir os passos 2-5 com uma classe nova, sem tocar nas tabelas
nem na Factory. Se o gateway novo NÃO suportar cartão salvo
(supportsSavedCardRecurring() = false), assinaturas recorrentes só
funcionam com o PagSeguro até esse gateway ganhar suporte — documentar
isso na tela de CRUD de gateways (task-11) pra o admin não ativar um
gateway incompatível como principal enquanto houver assinantes ativos.


5.1 POR QUE "RECORRÊNCIA MANUAL" (ORDERS API) E NÃO O PRODUTO
"ASSINATURAS" DO PAGBANK
------------------------------------------------------------------------
O PagBank tem DOIS jeitos de fazer recorrência (pesquisado em
developer.pagbank.com.br/docs/pagamentos-recorrentes):

  a) Produto "Assinaturas" (Planos + Assinantes + Assinaturas) — API
     SEPARADA (sandbox.api.assinaturas.pagseguro.com), com credencial
     própria ("chave pública exclusiva para recorrência"). O PagBank
     CONTROLA o ciclo e cobra sozinho, avisando via webhooks próprios
     (subscription.recurrence, .suspended, .canceled etc.). SÓ conta
     PJ aprovada pode usar via API (PF só tem a versão manual, sem
     API, pelo painel web) — exige contato com o time de Integrações
     do PagBank pra liberação em produção.
  b) Recorrência manual (mesma API de Orders já usada pro resto do
     projeto) — o COMERCIANTE dispara cada cobrança
     (card.encrypted + recurring.type=INITIAL na primeira, card.id +
     recurring.type=SUBSEQUENT nas seguintes). Sem API separada, sem
     credencial extra, sem exigência adicional de conta.

Escolhido (b) — encaixa exatamente no que a task-7 já desenhava
("cada renovação aprovada gera um novo order", scheduler diário) sem
precisar de uma segunda integração/credencial. A desvantagem é que
NÓS ficamos responsáveis por dar o "run" em cada cobrança (scheduler
já previsto na task-7) — mas isso já era assim no desenho original,
só não estava explícito COMO o cartão seria reutilizado a cada ciclo.


5.2 CARTÕES DE TESTE DO SANDBOX (developer.pagbank.com.br/docs/cartoes-de-teste)
------------------------------------------------------------------------------------------
Nunca usar cartão real em sandbox — o PagBank fornece uma tabela de
cartões fictícios que simulam aprovado/recusado automaticamente na
autorização, sem precisar de nenhum valor especial pra "forçar" o
resultado:

  Bandeira    | Nº do cartão      | CVV  | Validade | Resultado
  ------------|-------------------|------|----------|------------------
  Visa        | 4539620659922097  | 123  | 12/2026  | Aprovado (PAID)
  Visa        | 4929291898380766  | 123  | 12/2026  | Recusado
  Mastercard  | 5240082975622454  | 123  | 12/2026  | Aprovado (PAID)
  Mastercard  | 5530062640663264  | 123  | 12/2026  | Recusado
  Amex        | 345817690311361   | 1234 | 12/2026  | Aprovado (PAID)
  Amex        | 372938001199778   | 1234 | 12/2026  | Recusado
  Elo         | 4514161122113757  | 123  | 12/2026  | Aprovado (PAID)
  Elo         | 4389350446134811  | 123  | 12/2026  | Recusado
  Hiper       | 6062828598919021  | 123  | 12/2026  | Aprovado (PAID)
  Hiper       | 6062822916014409  | 123  | 12/2026  | Recusado

Como usar nos testes desta task (mapeando pro nosso recurring_type,
seção 1):

  - Checkout inicial aprovado (recurring_type='initial'): tokenizar
    com o cartão Visa "Aprovado" -> confirma que payment_method_tokens
    é criado e a subscription vira 'active'.
  - Checkout inicial recusado: tokenizar com o cartão Visa "Recusado"
    -> confirma que NÃO cria payment_method_tokens e a subscription
    fica 'incomplete' (nunca chega a 'active'), com mensagem de erro
    amigável (task-7).
  - Renovação aprovada (recurring_type='subsequent'): como o token
    salvo já existe (gerado no passo anterior com o cartão aprovado),
    chargeSavedMethod() reaproveita o MESMO card.id — pra testar uma
    renovação que falha, o teste precisa criar o payment_method_tokens
    inicial já a partir do fluxo com o cartão recusado simulado
    manualmente no factory/seed de teste (a API do PagBank não
    consegue "aprovar a 1ª e recusar a 2ª" pro mesmo cartão salvo — isso é
    simulado no NOSSO teste, mockando a resposta de chargeSavedMethod
    pra 'failed' na segunda chamada).
  - Reembolso: a doc do PagBank não lista cartão/valor especial pra
    reembolso — basta chamar o endpoint de reembolso normalmente
    contra um Order já 'paid' (criado com qualquer cartão "Aprovado"
    da tabela). Testar o fluxo completo: Order paga -> refund() ->
    Order vira 'refunded'.

O PagBank também tem cartões dedicados (D0/DN) pro produto nativo
"Assinaturas" simulando retry automático de cobrança — não se aplicam
aqui porque escolhemos recorrência manual (seção 5.1 acima): nosso
retry de renovação falhada é o comando subscriptions:renew tentando de
novo todo dia durante a carência (task-7), não um mecanismo do gateway.


5.3 PÁGINA DE CHECKOUT EMBEDDED (LACUNA CORRIGIDA — 2026-07-16)
------------------------------------------------------------------------
A task-7 só tinha o POST /planos/{plan}/assinar (processa) — faltava a
tela em si que MOSTRA o formulário de cartão antes disso. Corrigido:

  GET /planos/{plan}/checkout   (nova rota, ver task-7 seção 8)
    - Tela própria do projeto (não é redirect pro PagBank) com: resumo
      do plano escolhido + formulário de cartão (nome no cartão,
      número, validade, CVV) + botão "Assinar".
    - Inclui o script oficial do PagBank antes do </body>:
      <script src="https://assets.pagseguro.com.br/checkout-sdk-js/rc/dist/browser/pagseguro.min.js"></script>
    - Ao submeter, o JS da página chama PagSeguro.encryptCard() ANTES
      de qualquer requisição pro nosso backend:
        PagSeguro.encryptCard({
          publicKey: '{{ chave pública obtida via API — ver item abaixo }}',
          holder, number, expMonth, expYear, securityCode
        })
      Isso roda 100% no browser (a doc do PagBank confirma: "não
      requer chamada de servidor", é local) — o resultado é UM
      encryptedCard (string), e é só ISSO que vai no POST pro nosso
      backend. Número/CVV em texto puro NUNCA saem do browser, nunca
      chegam no Laravel — reduz nosso escopo de PCI DSS a
      praticamente zero (não armazenamos nem processamos cartão em
      texto puro em nenhum momento).
    - O formulário faz o POST /planos/{plan}/assinar (fetch/axios) só
      com { plan_id, encrypted_card: <resultado do encryptCard()> } —
      o Controller usa esse valor direto como card.encrypted na
      chamada da seção 3 acima.
    - A chave pública usada no JS NÃO é uma credencial copiada do
      portal (CORREÇÃO 2026-07-18: a página de tokens do sandbox,
      portaldev.pagbank.com.br/tokens, só mostra "E-mail" e "Token" —
      não existe campo "chave pública" pra copiar). Ela é gerada/
      consultada via API usando o próprio Bearer token:

        GET  https://sandbox.api.pagseguro.com/public-keys/card
             (consulta a chave já criada; 404 se ainda não existe)
        POST https://sandbox.api.pagseguro.com/public-keys
             corpo { "type": "card" }  (cria; 201 devolve public_key)
        Authorization: Bearer {token}  nos dois casos.

      O backend consulta primeiro (GET) e só cria (POST) se ainda não
      existir — POST repetido pode rotacionar a chave à toa. Como ela
      não muda a cada request, o backend guarda em cache e injeta só
      ELA na view do checkout — nunca o token/segredo da API, que
      fica só no backend. Portanto a ÚNICA credencial que o admin
      cadastra em payment_gateways.credentials é o Token de API; o
      e-mail exibido no portal é só o login da conta, não entra em
      nenhuma chamada da API.

Sem essa página, não existe como o usuário realmente pagar — este item
era uma peça faltando entre a decisão (checkout_mode='embedded') e a
implementação de fato.

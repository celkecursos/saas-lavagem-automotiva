TASK 13 - Testes automatizados (PHPUnit/Pest)
========================================================

OBJETIVO
--------
Cobrir com testes automatizados as regras de NEGÓCIO de maior risco
desenhadas nas demais tasks deste projeto (schema/domínio nas tasks 3
em diante) — não o CRUD trivial que o próprio Laravel já garante. Usar Pest (sintaxe padrão do Laravel 13, roda por cima do
PHPUnit), tudo executado via Sail, sem nada instalado fora do Docker.

Esta task NÃO é "escrever todos os testes só no final do projeto" — a
recomendação (seção 4) é escrever e rodar os testes de cada módulo
JUNTO da task correspondente. Este documento serve de referência da
estratégia e de checklist do que precisa estar coberto até o fim do
MVP.


1. FERRAMENTAS E CONFIGURAÇÃO
------------------------------------
- Pest já vem por padrão no scaffold do Laravel 13 (confirmar em
  composer.json: pestphp/pest, pestphp/pest-plugin-laravel).
- Banco de testes dedicado, nunca o de desenvolvimento/produção —
  mesma lição já conhecida no ecossistema Celke: RefreshDatabase apaga
  TUDO a cada teste. Configurar .env.testing com DB_DATABASE próprio
  (ex: celke_wash_club_test) via mysql do Sail — evitar sqlite
  in-memory aqui, porque o schema usa recursos que precisam se
  comportar igual ao MySQL real (JSON/encrypted em payment_gateways,
  enums, unique compostos) e sqlite diverge em detalhes desses casos.
- Rodar com: ./vendor/bin/sail artisan test  ou  ./vendor/bin/sail pest
- Criar factories (Model::factory()) pra todos os models envolvidos:
  User, Plan, PlanFeature, PaymentMethodToken, Subscription,
  SubscriptionCycle, CarWash,
  CarWashUser, CarWashInvitation, CarWashProductSubscription, Vehicle,
  PayoutPlan, WashRedemption, CarWashRating, CancellationRequest,
  PaymentGateway, PaymentGatewayType, Order, Payout, PayoutItem,
  ParkingLot, ParkingRate, ParkingSession, ParkingBillingSettings,
  ParkingBillingCharge, ReferralReward, Achievement, UserAchievement,
  LoyaltyRedemption, LoyaltyRedemptionClaim, OrderRefundRequest,
  RefundSetting.

3. TIPOS DE TESTE
----------------------
  - Feature tests (maioria): simulam a requisição HTTP completa
    (actingAs + post/get + assertStatus/assertDatabaseHas) — é o que
    dá confiança real de que o fluxo funciona ponta a ponta, não só
    que uma função isolada retorna certo.
  - Unit tests: só pra lógica isolada sem necessidade de banco/HTTP
    (ex: cálculo de valor do estacionamento dado duração + tarifa,
    cálculo de próxima data de renovação).
  - NÃO escrever teste pra getter/setter trivial do Eloquent nem pra
    rota que só faz CRUD sem nenhuma regra de negócio por trás —
    esforço sem retorno.

LOG DOS TESTES SEPARADO DO LOG DE DESENVOLVIMENTO
-----------------------------------------------------------
Vários testes exercitam caminho de erro de propósito (401 do PagBank via
Http::fake, checkout sem gateway ativo) e esses caminhos chamam
Log::warning/Log::error. Sem configuração, isso vai parar no MESMO
storage/logs/laravel.log do ambiente de desenvolvimento, e as linhas
aparecem assim:

  [.....] testing.ERROR: Checkout sem gateway de pagamento ativo... {"plan_id":360,"user_id":675}

Quem abre o log procurando um erro real perde tempo investigando uma
falha que nunca existiu. Aconteceu em 19/07/2026 exatamente assim.

Acrescentar em phpunit.xml:

  <env name="LOG_CHANNEL" value="null"/>

Log::spy()/Log::shouldReceive continuam funcionando: eles trocam a
facade inteira, não dependem do canal configurado.

Como reconhecer que uma linha do log veio de teste, e não da aplicação:
  - prefixo "testing." em vez de "local."
  - IDs fora de escala com o banco de desenvolvimento (plan_id 360 num
    banco que tem 3 planos) — factories acumulam IDs entre os testes
